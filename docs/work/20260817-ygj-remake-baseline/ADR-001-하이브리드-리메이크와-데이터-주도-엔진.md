## 요약

- 결정: 원작 파일을 추출하지 않고 엔진(로직·렌더·UI)을 신규 구현하며, 모든 게임 콘텐츠를 `data/` JSON으로 정의하고 엔진은 데이터의 해석기로 설계한다.
- 핵심 이유: 저작권 위험 최소화와 "병종 수정 시 데이터·UI 자동 반영"이라는 핵심 요구(FR-13)의 동시 충족.
- 주요 단점: 원작 수치를 커뮤니티 자료로 재구성해야 하며 감각 재현에 튜닝 비용이 든다.

## 배경

원작 재현 방법으로 원작 바이너리 추출·역공학, 기존 SRPG 제작 툴 활용, 신규 구현이 경쟁한다. 사용자는 개인 플레이 전용·원작 파일 미사용·자유로운 개조를 전제로 선행 명세에서 하이브리드 방식을 선택했고, 본 ADR은 그 결정과 근거를 기준선으로 기록한다.

## 영향을 받는 요구사항과 제약

- [FR-13](../../requirements.md) 데이터 주도·검증(핵심 요구사항), [NFR-02](../../requirements.md) 로직·렌더 분리, [NFR-06](../../requirements.md) 튜닝 가능성, [NFR-07](../../requirements.md) 저작권 준수.
- 제약: 원작 데이터는 커뮤니티 위키·공략 자료로 입력하고 불명확한 수치는 추정치+실측 튜닝으로 보정한다.

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| 원작 바이너리 추출·역공학 | 수치·맵 정확도 최고 | 저작권 위험, DOS 포맷 역공학 난이도, 개조 요구와 상충 | 높음 |
| 기존 SRPG 제작 툴(SRPG Studio 등) | 빠른 시작, 검증된 엔진 | 원작 고유 규칙(반격 없음·상성·책략 게이트) 커스터마이징 한계, 데이터→UI 자동 반영 구조 구현 곤란 | 중간 |
| 신규 엔진+데이터 주도 JSON (선택) | 규칙 완전 제어, 개조 용이, 웹 기술 재사용 | 전투 감각 튜닝 필요, 구현량 많음 | — |

## 결정

하이브리드 리메이크를 채택한다. 엔진은 신규 구현하고, 데이터는 커뮤니티 자료 기반 JSON으로 입력하며, 원작 파일 추출은 하지 않는다. 엔진 코드는 데이터의 해석기로만 동작한다.

## 이유

- 저작권 문제 소지를 최소화하면서(원작 파일 미사용) 원작 시스템 재현이 가능하다.
- 데이터 주도 구조만이 "병종 추가 시 엔진 수정 없이 데이터·UI 자동 반영"을 구조적으로 보장한다.
- 정확한 수치보다 "원작 감각"이 목표이므로 상수 외부화+실측 튜닝으로 충분하다.

## 결과와 감수할 단점

- 모든 콘텐츠 파일은 zod 스키마 검증과 참조 무결성 검사를 통과해야 한다(DES-03).
- 원작 수치 재구성·튜닝 비용을 감수한다(RISK-01). 데이터 입력 물량이 크다(RISK-03).
