## 요약

- 결정: TypeScript(strict)·Vite·PixiJS v8(맵/유닛 렌더)·HTML+CSS DOM 오버레이(메뉴 UI)·Zustand·zod·Vitest·Tauri v2(패키징)·Howler.js(사운드)를 채택한다.
- 핵심 이유: 웹 스택은 반복 속도(핫 리로드)와 방대한 SRPG UI 구현에 유리하고, Tauri로 윈도우·맥 양쪽 경량 패키징이 가능하다.
- 주요 단점: 네이티브 게임 엔진 대비 게임 특화 도구(씬 에디터 등)가 없어 직접 구현해야 한다.

## 배경

2D 턴제 SRPG를 개인이 장기 유지보수할 스택이 필요하다. 요구 특성: 방대한 메뉴·상태창 UI, 데이터 주도 구조와의 궁합, 윈도우·맥 배포, 결정론적 로직의 테스트 용이성. 선행 명세 [전체 설계 §1.4](../../../yeonggeoljeon-remake-design.md)에서 확정된 스택을 ADR로 기록한다.

## 고려한 대안

| 대안 | 장점 | 단점·위험 | 전환 비용 |
|---|---|---|---|
| Unity/Godot 등 게임 엔진 | 씬 에디터·에셋 파이프라인 내장 | DOM 수준의 UI 생산성 부재, 데이터 주도 UI 자동 반영 구현 부담, 개인 웹 기술 자산과 불일치 | 높음 |
| Electron + 웹 스택 | 웹 생산성 동일 | 번들 크기·메모리 큼, Tauri 대비 이점 없음 | 중간 |
| Vite+PixiJS+DOM UI+Tauri (선택) | 핫 리로드 반복, UI 생산성, 경량 패키징, TS 단일 언어 | WebView 편차(맥 WKWebView) 실기 검증 필요 | — |

## 결정

표의 선택안을 채택한다. 세부: 상태 관리 Zustand, 스키마 zod, 테스트 Vitest, 사운드 Howler.js. 개발 중 브라우저 실행, 완성 시 Tauri 패키징. 세이브는 개발 localStorage→패키징 Tauri fs로 전환(저장소 인터페이스 추상화).

## 이유

- SRPG는 UI 물량이 크고, DOM+CSS가 캔버스 UI보다 압도적으로 저렴하다(캔버스는 맵·유닛·이펙트에만 사용).
- zod 스키마가 "데이터 파일 검증"과 "TS 타입"을 한 곳에서 해결해 데이터 주도 원칙(ADR-001)과 맞물린다.
- Tauri v2는 윈도우·맥을 한 코드베이스로 커버하고 산출물이 경량이다.

## 결과와 감수할 단점

- 맵 에디터·애니메이션 상태 기계 등 게임 도구를 직접 구현한다(DES-05, DES-11).
- 맥 WKWebView의 오디오 정책·입력 차이를 M6에서 실기 검증한다(RISK-08).
- 의존성 버전은 lockfile로 고정하고 업그레이드는 별도 작업으로 분리한다(RISK-07).

## 후속 작업

- M0에서 Vite+TS+PixiJS 스캐폴딩과 validate 스크립트 구축(wf-implement 계획 소유).
